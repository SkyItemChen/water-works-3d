# 求解器与「最高分」的边界 · SOLVER LIMITS

> 用途：当有人报「我在第 X 关打出 N 分，表里只有 M」时，照这份清单排查。
> **结论先行：表里的分数是「搜索找到的最好解」，不是证明过的上界。** 任何一次「玩家比表高」都先当成求解器缺陷处理，而不是当成玩家记错。

相关代码：`src/game/core/solver.ts`（搜索）、`scripts/solve.mts`（跑批）、`scripts/merge-scores.mts`（合并）、`scripts/gen-challenge.mts`（生成 `src/levels/challenge.json`）、`scripts/verify-code.mts`（验码）。

---

## 1. 30 秒定位：差在「水」还是「块」

```
score = 10 × (清水排出 −  wasted) + 4 × 污水排出 − 2 × wasted + 15 × (blockLimit − 用块)
```

赢的瞬间冻结。所以先用关卡参数反推：

| 现象 | 含义 | 方向 |
|---|---|---|
| 差 **15 的整数倍**，且对方用块少 | 块序被重排（保留 / 更晚才用的垃圾块） | 查动作空间里的 **hold** |
| 差 15 的整数倍，块数相同 | 清水多排了 1.5 单位 | 查水路（管道/阀门朝向、短名单是否被截断） |
| 差**不是** 15 的整数倍 | 清水差几单位 | 查排水效率（结算时序、堤坝/死角处理） |
| 差 1–2 分 | 水位排空不彻底 | 先加预算，再查 `settle` 时序 |

第 1 关的历史例子：135 与 150，差 15 = 一块，因为块序 `soil2, pocket, soil2, soil2, sponge, pocket, pocket` 里第 3 个水囊原本是第 7 块。

## 2. 先验证对方（别先怀疑玩家）

```powershell
npm run verify -- WW3-XXXXXXXX...      # 玩家给的分享码
```

输出关卡、真实分数、用块、奖金、清水/污水，以及和 `challenge.json` 目标分的差。三种结论：

- `OK the table covers this line` → 表是对的，玩家记错或看的是别处。
- `ACTIONS the table is wrong` → 表偏低，按第 6 节复算。
- 解码失败 → 码被截断/改过，让他重新发。

## 3. 动作空间：已覆盖 / 未覆盖

一次「落点」= 旋转 × 列 × 时机，`expand()` 生成。**这里是所有历史踩坑的来源。**

| 动作 | 状态 | 说明 |
|---|---|---|
| 旋转 0–3（含墙踢 ∓2） | ✅ | `handleAction('C')` |
| 任意列 | ✅ | 出生行先横移到位，再等待/硬降 |
| 等待 0 / 70 / 160 tick 后硬降 | ✅ | `waits`，换排水时间 |
| 不砸、让重力把块放下去 | ✅ | `waits: -1`（上限 600 tick） |
| **保留 / 交换（hold）** | ✅ 2026-10-27 补 | 之前缺，导致全表普遍偏低一块（+15） |
| 同 tick 连续多动作（转向+平移+硬降） | ✅ | 引擎允许，求解器也这样生成 |
| **下落后再横移（tuck）** | ❌ | 边缘/悬挑下方能进的格子目前打不到 |
| 软降分段（逐格下移 + 中途改列） | ❌ | 与 tuck 同源 |
| 保留后再保留（同一块换两次） | ❌ | 引擎 `holdUsed` 也不允许，非缺陷 |
| 主动送水进错的口（有意的浪费换块数） | ⚠️ | 只在被评分函数选中的情况下才会出现 |

## 4. 搜索边界

- 三种策略并行：`seed`（1-ply greedy）、`settle`（每候选先结算 70 tick 再排名）、`wait`（先横移再等待）。三者都推进时钟 = **人类节奏**。
- `instant` / `chain` = tick 0 连锁硬降（硬降不吃 tick），引擎合法但人手做不到 → 只能 `--human` 关闭，或标 `pace: 'machine'`（生成器默认拒绝）。
- beam 宽默认 `10, 30`，`perNode` 默认 6，单关预算 `--time`（毫秒）；预算用尽会**中途收线**，分数会更低。
- 状态去重：`grid + 水位(1/8 量化) + blocksUsed + hold + next[0]`。
- **没有证明能力**：`upperBound()` 是解析上界（零浪费、全部水入账），通常比实际高 100–700，只能用来判断"还有多少空间"。

## 5. 已知失效模式（症状 → 原因 → 处置）

| 症状 | 原因 | 处置 |
|---|---|---|
| 表比玩家低 15 且块更少 | 缺 hold（**已修**） | `stateSig` 要带 `hold/next[0]`，否则带保留槽的重复状态会被合并掉 |
| 管道/阀门关（c18 一类）整关解不出 | 短名单按「分数」取样 → 40 个管道候选里只剩"朝下"的 | 短名单按**旋转 × 列均匀取样**，别按分数 |
| 整关 `unknown`，节点数没触到 deadline | 时序模型不对（先结算再横移 vs 先横移再等） | 两种策略都要跑，缺一个就会漏半关 |
| 水位停在 6.2/8 不动 | 排水需要长时间渗透，早退就废 | `settle` 有最小 tick 下限（≥70） |
| 分数差 1–2 分 | 结算截断，水没排完 | 加 `--time`，或看 `settle` 尾部 |
| 玩家用了下落后横移 | tuck 缺失（未实现） | 需要加动作，见第 3 节 |

## 6. 复算流程（发现表偏低）

```powershell
# 1. 先单关深挖，确认是人类节奏
npm run solve -- --level c07 --human --time 60000 --per-node 10 --beam 12,36 --out scripts/out/fix-c07.json

# 2. 与现有最高分合并（每关取最高，平分时优先人类节奏）
npm run merge:scores -- scripts/out/maxScores.json scripts/out/fix-c07.json

# 3. 重新生成挑战数据（会逐条 encode→decode→replay 校验）
npm run gen:challenge

# 4. 必须跑测试：challenge.test 会把 60 条官方码全部回放一遍
npm test
```

`--human` 是硬要求：目标分只能是人类能复现的线，`instant`/`chain` 会被生成器拒绝（除非显式 `--allow-machine`，然后 UI 打「机器线」标）。

## 7. 改动关卡后的连带责任

改地形 / 目标 / 种子会让该关的**旧分享码与旧回放全部失效**（水位与地形变了，回放会分叉），同时 `challenge.json` 里的目标分与官方码必须重新生成。目前没有版本化回放，所以只对未发布的关卡这么做。
